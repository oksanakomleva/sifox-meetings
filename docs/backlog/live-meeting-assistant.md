# Беклог: живой ассистент в встрече («Протоколлер, …» → голосовой ответ)

> Статус: **частично реализовано, на паузе** (продолжим позже). План согласован 2026-06-17, реализация начата 2026-06-18.

## Статус реализации (на 2026-06-18)

Реализовано и **проверено на проде** (за флагами `LIVE_ASSISTANT_ENABLED` / `LIVE_ASSISTANT_SPEAK`):
- Фазы 0–2 целиком: слушание комнаты (второй `parec` с монитора), ловля кодового слова `tiny`-моделью, распознавание вопроса `small`, выбор scope (full/meeting_only по доменам участников + флаг ведущего), QA по встречам+MM+почте, запись в `live_qa`. Эндпоинт `GET /api/admin/meetings/{id}/live-qa` (тест-ключ).
- **Доказанный end-to-end full-scope ответ**: вопрос «когда отправлен бриф по Сберу» → ответ «11 июня 2026» из почты (meeting `21fd5a19`).
- Фаза 3 частично: кнопка микрофона Телемоста находится и кликается (`Bot mic: clicked button[aria-label*='икрофон']`), TTS (OpenAI) синтезируется и подаётся в виртуальный мик (`spoke answer into botmic_…`).
- Коммиты: `6f574d9` (0–2), `e60828d` (организатор=участник→scope), `682e8a2` (предзагрузка tiny/small в образ), `8723d68` (admin live-qa endpoint), `ccc896b` (Фаза 3 TTS), `5e3de78` (срез контекста для скорости).

**Открытые проблемы (продолжить отсюда):**
1. **Звук не слышен в комнате / мик бота не включается реально.** Клик по кнопке логируется, но участник не слышит ответ и индикатор мика Protocaller не загорается. Гипотезы: в тулбаре ДВЕ кнопки «Включить микрофон» — `.first` может быть не та (нужно выбирать именно in-call контрол); и/или Chromium не берёт `botmic.monitor` как устройство ввода (надо явно выбрать source для getUserMedia / проверить, что мик реально transmit). Тулбар-лейблы из лога: `['Ещё','Настройки','Войти','Включить микрофон','Пригласить на встречу','Включить микрофон','Включить камеру','Поднять руку','Начать демонстрацию экрана','Участники','Открыть чат','Ещё','Выйти из встречи']`.
2. **Точность распознавания вопроса.** `small` на CPU искажает имена собственные: «Сбер»→«Взбер» → FTS не находит. Решение: модель крупнее / OpenAI Whisper API для вопроса.
3. **Задержка ~15–20 c** (с ~60 c после среза контекста `5e3de78`). Дальше: ускорить STT вопроса (Whisper API), возможно стримить TTS.
4. **UI (Фаза 4):** лента «Вопросы ассистенту» в карточке встречи + тумблер `assistant_full_access` для ведущего — не сделаны.

**ВАЖНО на время паузы:** в Railway сейчас включены `LIVE_ASSISTANT_ENABLED=true` и `LIVE_ASSISTANT_SPEAK=true` — то есть на КАЖДОЙ записи бот слушает и **кликает кнопку микрофона**. На реальных встречах это нежелательно. Рекомендуется **выключить `LIVE_ASSISTANT_SPEAK` (и `LIVE_ASSISTANT_ENABLED`)** до возобновления работы.

## Context
Во время встречи участник говорит кодовое слово **«Протоколлер»** + вопрос (напр. «когда отправили документы?»). Бот распознаёт фразу после кодового слова, ищет ответ и **отвечает голосом** (TTS) в комнату. Real-time поверх текущего пакетного конвейера. За флагом включения.

**Дёшево по CPU:** непрерывно слушаем лёгкой моделью whisper **tiny** на коротких окнах (~3 c) только ради детекции слова; точную модель — РЕДКО, только на сам вопрос после триггера.

## Модель приватности (ключевое)
«Внешний» определяется по `attendee_emails` из календарного события: есть домен ≠ `sifox.com` → встреча внешняя (логика уже есть, ср. `get_meeting_attendee_emails`).
- **Внутренняя встреча** (все @sifox.com) → **полный режим**: источники = прошлые встречи + Mattermost + почта; ответ голосом. Без трения (основной кейс).
- **Встреча с внешними** → **безопасный режим**: ассистент отвечает голосом **только по живому буферу текущей встречи** (что сказано после захода бота); архив встреч / почта / MM **недоступны**.
- **Ручной обход:** ведущий может переключателем в нашем вебе разрешить **полный режим** на конкретной внешней встрече (доверенный гость).
- **Аудит (всегда):** логируем каждый вопрос, режим и какие источники использованы (видно админу).

«Живой буфер» возможен потому, что фича и так слушает вживую: копим черновой транскрипт из tiny + держим кольцевой аудио-буфер последних ~10 мин (≈12 МБ) для точного до-распознавания по запросу.

## Что переиспользуем
- **Аудио/PulseAudio:** `_create_pulse_sink`/`_set_default_sink`/`AudioCapture`, монитор синка (`backend/services/recorder.py`).
- **«Бот говорит» — прецедент:** тест-спикер (`--use-file-for-fake-audio-capture`) + `paplay --device {sink}` (`backend/api/admin.py`, `backend/tests/e2e/test_speaker.py`).
- **Поиск:** `search_mm_messages`, `search_email_messages`, `get_recent_meetings_with_transcripts` (`backend/database/models.py`); определение внешних — паттерн `get_meeting_attendee_emails`.
- **Генерация:** retrieval→OpenAI как в `backend/api/communications.py` (`config.CHAT_MODEL`, non-stream).
- **Транскрипция:** `transcribe_audio`/faster-whisper (`backend/services/transcriber.py`) + загрузка `tiny`.

## Фаза 0 — конфиг и гейтинг
- `config.py` (+`.env.example`), Optional с дефолтами: `LIVE_ASSISTANT_ENABLED=False`, `LIVE_WAKE_WORD="протоколлер"`, `LIVE_WAKE_MODEL="tiny"`, `LIVE_QUESTION_MAX_SEC=10`, `LIVE_BUFFER_MIN=10`, `LIVE_TTS="openai"` (fallback `espeak`).
- Live-цикл стартует в `_record_pipeline` только при `LIVE_ASSISTANT_ENABLED`.

## Фаза 1 — слушание, кодовое слово, живой буфер (`backend/services/live_assistant.py`, новый)
- **Тап звука:** второй `parec --device {sink}.monitor -format s16le -rate 16000 -channels 1` параллельно основному (монитор допускает несколько читателей — WAV не страдает).
- Фоновая задача `listen_loop(meeting_id, sink_name)` рядом с `track_speakers`, отменяется в конце.
- Кольцевой аудио-буфер последних `LIVE_BUFFER_MIN` минут. Каждые ~2 c прогон **tiny** по последним ~3–4 c → текст: (а) копится в черновой «живой транскрипт»; (б) проверка на основу «протокол» → триггер.
- После триггера: захватить речь после слова до паузы/`LIVE_QUESTION_MAX_SEC` → распознать точно (medium/OpenAI Whisper) → текст вопроса.
- Дебаунс: на время обработки и проговаривания ответа слушатель на паузе.

## Фаза 2 — QA-движок c областью доступа (`backend/services/qa_engine.py`, новый)
- `answer_question(question, meeting_id, scope) -> str`, где `scope ∈ {full, meeting_only}`:
  - `full`: retrieval параллельно — `search_mm_messages`, `search_email_messages`, `get_recent_meetings_with_transcripts(90д)`; ранжирование+бюджет как в comms; + живой буфер текущей встречи.
  - `meeting_only`: контекст = **только живой буфер** этой встречи (при необходимости до-распознать последние минуты из аудио-буфера точной моделью). Никаких внешних источников.
  - Генерация: `AsyncOpenAI` `CHAT_MODEL`, system «отвечай очень кратко — это произносится голосом; 1–2 предложения; если данных нет — скажи»; небольшой `max_tokens`; non-stream.
- Определение `scope`: внешние по attendee_emails → `meeting_only`, иначе `full`; ручной флаг ведущего (Фаза 4) форсит `full`.
- Аудит: писать (meeting_id, время, вопрос, режим, источники, ответ).

## Фаза 3 — голосовой ответ в встречу (TTS) ⚠ самый рискованный шаг
- **Виртуальный микрофон бота:** создавать `module-null-sink` (`botmic`) **в рантайме через `pactl load-module` при старте встречи** (как уже делается per-meeting sink) — НЕ править `entrypoint.sh`, чтобы не влиять на глобальный старт контейнера. Его `.monitor` как source; задать дефолтным source до запуска браузера бота; Playwright-контекст `permissions=["microphone"]`.
- В `_join_meeting`: включать мик бота **только при ассистенте** (сейчас выключен — включение вызывало модалки прав; делать аккуратно или входить с mute и размучивать на время ответа).
- **TTS:** `openai` (`audio.speech.create`, рус. голос) → WAV; fallback `espeak-ng` (офлайн, уже в образе).
- **Воспроизведение:** `paplay --device botmic` → попадает в мик бота → Телемост транслирует. На время: пауза слушателя, (опц.) размут/мут.
- Ответ попадёт и в WAV → в посттранскрипт; пометить «Protocaller (AI)».

## Фаза 4 — UX / переключатель / наблюдаемость
- **Переключатель ведущего:** в детали встречи (наш веб) — тумблер «Полный доступ ассистента на этой встрече» (для внешних встреч); читается рекордером в реальном времени (поле в БД, напр. `meetings.assistant_full_access`).
- Список «Вопросы ассистенту» (Q/A + режим + таймкоды) в деталях встречи.
- Kill-switch: глобальный флаг; лог каждого триггера/вопроса/ответа/режима.

## Влияние на текущую работоспособность (изоляция) — обязательно
- **Глобальный флаг `LIVE_ASSISTANT_ENABLED` (default OFF):** при выключенном флаге поведение рекордера/конвейера идентично текущему; мердж с OFF ничего не меняет в проде.
- **Полная изоляция `listen_loop`:** отдельная asyncio-задача со своим `try/except`; любое её падение логируется и НЕ прерывает запись/основной конвейер. Второй `parec` читает `.monitor` (несколько читателей допустимо) — основной захват WAV не затрагивается.
- **Join-флоу:** при OFF путь входа и микрофон — байт-в-байт как сейчас (мик выключен). Включение мика — только под флагом (Фаза 3), причина текущего «мик OFF» — модалки прав, блокировавшие вход.
- **transcriber:** существующий `transcribe_audio` не меняем (только добавляем функции/ленивую загрузку `tiny`); следим за RAM (риск OOM при записи).
- **Схема БД:** только идемпотентные `CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS`; существующие столбцы не трогаем.
- **Роллаут:** реализовать → задеплоить с флагом OFF (проверить, что ничего не изменилось) → включить на одной тест-комнате/встрече → понаблюдать CPU/RAM/латентность → расширять. Фаза 3 валидируется на тест-комнате до любого прод-включения.

## Верификация
- Юнит: матчер кодового слова; выбор `scope` по составу участников; сборка контекста (чистые части).
- E2E через speaker-харнесс: `espeak-ng` WAV «Протоколлер, когда отправили документы?» проиграть тест-спикером в тестовую комнату → wake пойман, вопрос распознан, `qa_engine` ответил, TTS проигран и записан. Прогон на Railway.
- Сценарии приватности: внутренняя встреча → отвечает по почте/MM; встреча с внешним → отвечает только по сказанному в комнате; тумблер ведущего → полный доступ; всё пишется в аудит.
- Ручное: реальная встреча — кодовое слово + вопрос, услышать ответ; проверить задержку и ложные срабатывания.

## Риски
- Задержка/CPU live-STT (смягчено: tiny + короткие окна + точная STT только после wake).
- Включение мика бота может вернуть модалки прав Телемоста — аккуратно; фолбэк-каналы ответа при ненадёжности.
- Ложные срабатывания wake-word; русский ASR на коротких/шумных окнах.
- Изменения вёрстки Телемоста.

## Порядок (рекомендация)
Фаза 0→2 с ответом **текстом** (в лог/веб) для проверки качества распознавания и ответов и модели приватности; затем Фаза 3 (голос в встречу) — самый рискованный аудио-плумбинг — отдельным шагом на тест-комнате. Так быстро получаем рабочий контур, не блокируясь на роутинге звука.

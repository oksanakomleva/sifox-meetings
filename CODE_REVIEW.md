# Code review: telemost-web

Дата ревью: 2026-07-23

## Цель и контекст

Проведено статическое ревью проекта с фокусом на:

- зависание сервиса и прекращение ответов;
- невозможность загрузить запись через браузерное расширение;
- безопасность, отказоустойчивость и потенциальные проблемы эксплуатации.

Исходный код в рамках ревью не изменялся.

## Статус исправлений на 2026-07-27

Исправления подготовлены локально, без commit/push:

- закрыт path traversal в SPA fallback;
- OAuth consent привязан к исходной web-сессии и Google identity;
- upload расширения переведён на небольшие возобновляемые chunks;
- неподтверждённые chunks сохраняются в IndexedDB и повторно отправляются после
  сетевого сбоя или перезапуска service worker;
- неудачный запуск MediaRecorder отменяет пустую серверную upload-сессию и не
  блокирует следующую запись;
- для пользовательского адреса Sifox расширение теперь запрашивает точечное
  разрешение Chrome, поэтому смена домена deployment не ломает login/upload;
- старый цельный upload расширения использует общий off-loop service;
- добавлены ограничения размера, параллельных сохранений и активных upload jobs;
- фоновые upload jobs участвуют в graceful shutdown/recovery;
- Markdown renderer больше не использует недоверенный raw HTML;
- добавлены DB command timeout и readiness-проверка;
- storage I/O вынесен в отдельный bounded executor;
- debug screenshots закрыты admin authentication;
- public-share limiter ограничен по памяти;
- Chromium/media processing запускаются от непривилегированного пользователя,
  sandbox включён по умолчанию;
- исправлена проверка доступа к одной встрече без лимита в 1000 записей.

Локально прошли 79 backend-тестов, Python compilation, production-сборка
frontend, TypeScript check и проверка синтаксиса JavaScript расширения.

Перед production deploy всё ещё обязательны:

- сборка Docker image (локальный Docker daemon во время работы был выключен);
- smoke test подключения Chromium с sandbox в Railway;
- реальная длинная запись через установленное расширение;
- тест обрыва сети и повторного завершения upload;
- проверка прав Railway volume для нового непривилегированного пользователя.

## Краткий вывод

Наиболее вероятная общая причина двух наблюдаемых проблем находится в
`backend/api/extension.py`: endpoint расширения синхронно записывает файл на
сетевой `AUDIO_DIR` внутри единственного event loop. Если сетевой том
задерживается, весь сервис перестаёт отвечать. Через 90 секунд watchdog завершает
процесс, поэтому загрузка расширения обрывается.

В обычном web uploader эта проблема уже частично исправлена через off-loop I/O,
но endpoint расширения сохранил старую копию логики.

Помимо этого найдены две критические уязвимости:

1. Возможность выхода за пределы каталога frontend при раздаче файлов.
2. Возможность привязать Google Calendar или Gmail другого человека к своему
   аккаунту через неподтверждённый OAuth flow.

## Приоритет исправлений

1. Закрыть path traversal в SPA fallback.
2. Привязать OAuth state к исходной web-сессии и Google identity.
3. Перевести upload расширения на общий безопасный upload service.
4. Сделать загрузку расширения возобновляемой и не хранить всю запись в RAM.
5. Закрыть stored XSS в Markdown renderer.
6. Ввести ранние лимиты upload, квоты и ограниченную очередь обработки.
7. Добавить DB timeouts и корректную readiness-проверку.
8. Исправить модель файловых timeout и изоляцию Chromium.
9. Закрыть debug screenshots и исправить rate limiting.

## [P0] Path traversal в публичном SPA fallback

Файл: `backend/main.py`, строки 139–145.

### Проблема

`full_path` напрямую присоединяется к `frontend/dist`, после чего проверяется
только `os.path.isfile(candidate)`. Нет проверки, что нормализованный итоговый
путь остался внутри `frontend/dist`.

URL с закодированными компонентами `../` потенциально позволяет выйти в
соседние каталоги и прочитать файлы, доступные процессу.

### Влияние

- Endpoint доступен без авторизации.
- Возможна утечка конфигурации, исходного кода и служебных файлов контейнера.
- В зависимости от окружения утечка может помочь получить секреты или доступ к
  другим системам.

### Требуемое исправление

- Вычислять `resolve()` для корня и кандидата.
- Проверять принадлежность кандидата корню через `relative_to()` или эквивалент.
- Предпочтительно передать раздачу статических файлов стандартному
  `StaticFiles`, оставив отдельный безопасный SPA fallback.
- Добавить тесты с URL-кодированными `../`, encoded slash и абсолютными путями.

### Что изменится для пользователей

Обычная навигация и статические файлы продолжат работать. Запросы за пределы
frontend будут получать 404 или 403.

## [P0] OAuth account-linking CSRF

Файлы:

- `backend/auth/google_oauth.py`, строки 46–49 и 174–208;
- `backend/api/auth.py`, endpoints подключения Calendar и Gmail.

### Проблема

OAuth state хранит назначение операции и `user_id`, но не связан с web-сессией,
которая начала подключение. Callback не требует ту же сессию и не сверяет
полученный Google `sub`/email с пользователем, для которого сохраняется токен.

Возможный сценарий:

1. Пользователь A начинает подключение Calendar или Gmail.
2. Передаёт Google consent URL пользователю B.
3. B авторизуется и предоставляет доступ.
4. Google-токены B сохраняются для аккаунта A.

### Влияние

- Calendar пользователя B может синхронизироваться в аккаунт A.
- A потенциально получает доступ к встречам и связанным данным B.
- Для Gmail может появиться возможность отправлять почту через аккаунт B.

### Требуемое исправление

- Хранить вместе со state хеш или идентификатор исходной session.
- В callback требовать и проверять ту же активную session.
- Проверять ожидаемый Google `sub` и/или email перед сохранением токенов.
- Делать state одноразовым, короткоживущим и хранить в БД/Redis либо в
  подписанном сервером формате.
- Добавить негативный тест: consent завершается из другой сессии.

### Что изменится для пользователей

Подключение Google продолжит работать, но завершить его можно будет только в том
же аккаунте и браузерной сессии, где оно было начато.

## [P1] Upload расширения блокирует весь event loop

Файл: `backend/api/extension.py`, строки 115–141.

### Проблема

Endpoint выполняет синхронные операции `os.makedirs`, `open`, `write` и `unlink`
на сетевом `AUDIO_DIR` внутри единственного event loop.

Это тот же класс проблемы, который уже исправлялся для обычного uploader через
`services/fsio.py` и `services/uploads.py`, но endpoint расширения использует
отдельную устаревшую реализацию.

### Влияние

- При задержке сетевого тома перестаёт отвечать весь сервис.
- Останавливаются API и фоновые задачи.
- Watchdog через 90 секунд аварийно завершает процесс.
- Текущая загрузка расширения получает разрыв соединения.
- Пользователь теряет запись, потому что retry отсутствует.

### Требуемое исправление

- Удалить дублирование upload flow.
- Использовать общий `save_upload_and_process` либо новый общий service.
- Изолировать файловое сохранение от event loop.
- Ограничить время, размер и concurrency сохранения.
- Возвращать пользователю стабильный upload/job ID.
- Добавить интеграционный тест с искусственно зависающим файловым хранилищем:
  `/health` и другие API должны продолжать отвечать.

### Что изменится для пользователей

Проблема одной загрузки перестанет останавливать сервис для всех. При недоступном
хранилище конкретная загрузка получит контролируемую ошибку или будет повторена.

## [P1] Расширение хранит всю запись в оперативной памяти

Файл: `extension/offscreen.js`, строки 4–5, 65 и 82–119.

### Проблема

Все секундные chunks MediaRecorder хранятся в массиве до окончания встречи.
После остановки создаётся дополнительный большой `Blob`, который затем целиком
передаётся в `fetch`.

После неуспешной загрузки recorder очищается. Персистентной копии, retry и
возобновления загрузки нет.

### Влияние

- Многочасовая встреча может занять сотни мегабайт RAM.
- Chrome/offscreen document может завершиться из-за нехватки памяти.
- Временный сетевой сбой приводит к потере всей записи.
- Пользователь не может повторить upload без сохранившегося файла.

### Требуемое исправление

- Периодически сохранять chunks в IndexedDB или отправлять на сервер.
- Реализовать resumable/chunked upload с upload ID.
- Хранить очередь незавершённых загрузок и повторять их после восстановления сети.
- Показывать пользователю состояния «сохранено локально», «загружается»,
  «нужен повтор».
- Не очищать локальную запись до подтверждённого завершения сервера.

### Что изменится для пользователей

Длинные записи перестанут зависеть от объёма RAM и одного непрерывного HTTP
запроса. После временной ошибки загрузку можно будет продолжить.

## [P1] Stored XSS в AI-протоколах

Файл: `frontend/src/components/MarkdownRenderer.tsx`, строки 21–40.

### Проблема

`boldify()` подставляет HTML-теги без предварительного escaping, а результат
передаётся в `dangerouslySetInnerHTML`.

AI summary нельзя считать доверенным: транскрипт формируется из речи участников,
и через prompt injection модель может вернуть произвольный HTML.

### Влияние

- Вредоносный HTML может выполниться при открытии протокола.
- Код будет работать в контексте авторизованного пользователя.
- Уязвимость затрагивает Meeting Detail и публичный Share View.

### Требуемое исправление

- Использовать Markdown renderer, который по умолчанию запрещает raw HTML.
- Либо сначала HTML-escape весь ввод, затем безопасно применять поддерживаемую
  Markdown-разметку.
- Если raw HTML действительно нужен, использовать строгую sanitization с
  минимальным allowlist.
- Добавить тесты для `<img onerror>`, `<svg onload>`, ссылок `javascript:` и
  сломанной Markdown-разметки.

### Что изменится для пользователей

Заголовки, списки и жирный текст сохранятся. Опасные HTML-конструкции будут
показаны как текст или удалены.

## [P1] Лимит upload применяется после приёма multipart body

Файлы:

- `backend/api/extension.py`, строки 79–141;
- `backend/services/uploads.py`, строки 33–95.

### Проблема

FastAPI разбирает multipart и создаёт `UploadFile` до входа в обработчик. Лимит
500 МБ проверяется только во время повторного копирования уже принятого файла.

Нет пользовательских квот, ограничения количества параллельных загрузок и
ограниченной очереди обработки.

### Влияние

- Файл больше 500 МБ всё равно может заполнить временный диск.
- Активный или скомпрометированный пользователь может заполнить `AUDIO_DIR`.
- Можно накопить неограниченное число фоновых задач транскрибации.
- CPU, диск и БД могут быть истощены без формального превышения одного лимита.

### Требуемое исправление

- Ограничить request body на reverse proxy/ASGI middleware до multipart parser.
- Ввести квоты по пользователю и общий storage budget.
- Ограничить число одновременно сохраняемых и обрабатываемых записей.
- Перенести обработку в персистентную bounded queue.
- Проверять реальный контейнер/кодек через `ffprobe`, а не только расширение имени.

### Что изменится для пользователей

Слишком большой файл будет отклонён сразу с понятной ошибкой. Нормальные загрузки
не будут конкурировать с неограниченным числом тяжёлых задач.

## [P1] Filesystem timeout не останавливает зависший thread

Файл: `backend/services/fsio.py`, строки 25–26.

### Проблема

`asyncio.wait_for(asyncio.to_thread(...))` прекращает ожидание после timeout, но
не может остановить уже выполняющийся системный вызов в потоке.

При зависшем сетевом томе такой thread может остаться занят навсегда. Повторные
операции постепенно исчерпают default executor.

### Влияние

- Перестают запускаться другие `to_thread`/default executor операции.
- Может зависнуть Google sync и часть файловых операций.
- Основной event loop формально жив, поэтому watchdog может не сработать.
- Сервис оказывается частично неработоспособным, оставаясь «здоровым».

### Требуемое исправление

- Не считать `wait_for(to_thread())` жёсткой отменой.
- Использовать отдельный bounded executor или изолированный process для storage I/O.
- Настроить mount-level/network timeout, если это поддерживается хранилищем.
- Добавить circuit breaker: после нескольких timeout временно не запускать новые
  операции на томе.
- Экспортировать метрики числа активных/зависших storage операций.

### Что изменится для пользователей

Сбой сетевого тома не будет постепенно отравлять весь процесс. После
восстановления хранилища сервис сможет продолжить работу без ручного redeploy.

## [P1] Нет DB timeout и корректной readiness-проверки

Файлы:

- `backend/database/connection.py`, строки 16–21;
- `backend/main.py`, строки 110–117.

### Проблема

Пул asyncpg создаётся без `command_timeout`. Ожидание соединения и большинство
запросов не имеют deadline.

`/health` проверяет только in-memory состояние recorder и не обращается к БД,
хранилищу или фоновым задачам.

### Влияние

- Зависшие запросы могут занять все 10 соединений.
- Следующие запросы будут ждать свободное соединение неопределённое время.
- `/health` продолжит возвращать `ok`.
- Railway не исключит неработоспособный экземпляр из трафика.

### Требуемое исправление

- Настроить `command_timeout`.
- Добавить ограниченное время ожидания `pool.acquire()`.
- Разделить:
  - liveness: процесс/event loop жив;
  - readiness: короткий DB ping, состояние критических сервисов и очередей.
- Не выполнять долгие проверки внутри liveness.
- Добавить метрики pool size, acquired, waiting и query timeout.

### Что изменится для пользователей

При проблеме БД запрос завершится контролируемой ошибкой, а не бесконечным
ожиданием. Платформа сможет перестать направлять трафик в неготовый экземпляр.

## [P1] Chromium работает от root без sandbox

Файлы:

- `Dockerfile`: отсутствует инструкция `USER`;
- `backend/services/recorder.py`, строки 330–340.

### Проблема

Контейнер работает от root, а Chromium запускается с `--no-sandbox` и
`--disable-setuid-sandbox`.

Браузер открывает внешние страницы встреч. Также сервис обрабатывает
пользовательские медиафайлы через ffmpeg и Whisper.

### Влияние

- Эксплуатация уязвимости Chromium даёт широкие права внутри контейнера.
- Потенциально доступны секреты окружения и сетевые credentials.
- Уязвимость медиапарсера также имеет повышенное воздействие.

### Требуемое исправление

- Создать непривилегированного пользователя контейнера.
- Выдать только необходимые права на `AUDIO_DIR`, `/tmp` и runtime directories.
- По возможности включить Chromium sandbox.
- Если sandbox несовместим с платформой — вынести browser/media processing в
  отдельный worker с минимальными секретами и сетевыми правами.
- Добавить CPU, RAM, process и filesystem limits.

### Что изменится для пользователей

Функциональность записи должна остаться прежней. Снизится влияние возможной
уязвимости браузера или медиапарсера.

## [P2] Debug screenshots доступны без авторизации

Файлы:

- `backend/main.py`, строки 120–130;
- `backend/services/recorder.py`, строки 569–665.

### Проблема

Публичный endpoint отдаёт debug screenshots и перечисляет имена доступных
файлов. Скриншот `3-after-join` создаётся после входа во встречу.

Комментарий `no PII` неверен: на экране могут присутствовать название встречи,
имена участников и другие данные интерфейса.

### Влияние

Неавторизованный посетитель потенциально получает конфиденциальную информацию о
встречах.

### Требуемое исправление

- Удалить endpoint из production либо закрыть admin authentication.
- Не возвращать список файлов анонимному пользователю.
- Использовать уникальные имена с meeting ID и случайной частью.
- Автоматически удалять screenshots через короткий TTL.

### Что изменится для пользователей

На обычную работу сервиса правка не повлияет. Администраторы при необходимости
будут открывать диагностику после авторизации.

## [P2] Публичный rate limiter создаёт неограниченный словарь

Файл: `backend/api/share.py`, строки 23–35.

### Проблема

`_attempts` получает запись до проверки существования share token. Истёкшие
записи очищаются только при повторном обращении к тому же token и не имеют
общего предела.

### Влияние

- Запросы с уникальными случайными token постоянно увеличивают потребление RAM.
- Возможен OOM и перезапуск процесса.
- После рестарта все ограничения попыток сбрасываются.
- Лимит по token не защищает от распределённого перебора.

### Требуемое исправление

- Проверять формат и существование token до добавления счётчика.
- Использовать bounded TTL cache или внешний rate limiter.
- Ограничивать по комбинации IP, token и временного окна.
- Не раскрывать различия, облегчающие перебор действительных ссылок.

### Что изменится для пользователей

Легитимные пользователи по-прежнему будут защищены от перебора пароля, но
случайные запросы не смогут бесконечно увеличивать память процесса.

## Дополнительные замечания

### Синхронный I/O остался в других местах

Следует отдельно проверить:

- `backend/services/megafon_sync.py`, сохранение скачанного файла;
- storage endpoints в `backend/api/admin.py`;
- прямые `exists/stat/remove` на `AUDIO_DIR`.

Операции на локальном `/tmp` менее рискованны, чем операции на сетевом
`AUDIO_DIR`.

### OAuth state store не очищается

`_states` и `_next_paths` находятся в памяти процесса. Истёкшие state не
удаляются глобально. Публичные запросы к `/api/auth/login` могут постоянно
увеличивать словарь. Кроме того, все незавершённые OAuth flow теряются при
restart/deploy.

### Фоновые задачи недостаточно наблюдаемы

`/health` не проверяет, что scheduler и sync loops всё ещё выполняются.
Завершившаяся с ошибкой фоновая задача может остаться незамеченной.

Следует хранить task references, логировать unexpected completion и экспортировать
время последнего успешного цикла каждого worker.

### Настраиваемый baseUrl расширения фактически ограничен

`extension/manifest.json` содержит host permissions только для production URL и
localhost. Если пользователь укажет другой deployment URL, cookies/fetch могут
быть заблокированы Chrome.

Либо убрать настройку baseUrl, либо синхронизировать её с допустимыми
host permissions.

### Проверка доступа к встрече ограничена 1000 строками

`backend/api/meetings.py::_get_accessible_meeting` загружает до 1000 доступных
встреч и строит set ID в Python. Пользователь с большим количеством встреч может
получить ошибочный 403 для старой встречи.

Проверку доступа лучше выполнять отдельным SQL `EXISTS` для конкретного
`meeting_id`.

## Критерий завершения исправления текущего инцидента

Исправление upload нельзя считать завершённым только после успешной загрузки
небольшого тестового файла. Необходимо подтвердить:

1. Загрузка длинной записи не удерживает всю запись в RAM.
2. Временный сетевой сбой не уничтожает локальную запись.
3. Загрузка может быть повторена или продолжена.
4. Искусственная задержка `AUDIO_DIR` не блокирует `/health` и остальные API.
5. Перезапуск backend во время upload не оставляет встречу навсегда в
   `transcribing`.
6. Одновременные загрузки ограничены и не могут заполнить диск или очередь.
